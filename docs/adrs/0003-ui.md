# ADR 0003 — UI

- **Status:** Aceito
- **Data:** 2026-07-24
- **Decisores:** Vinicius
- **Relaciona:** [ADR 0001 — Arquitetura Geral](0001-arquitetura-geral.md)

## Contexto

A UI precisa ser simples de manter e testar, sem SSR, e apresentar dois módulos
do MVP — **Daily Log** e **Analyse** — dentro de um app desktop (Tauri). Ela deve
consumir apenas os use-cases/ports do domínio, sem conhecer detalhes de
persistência.

## Decisão

### Stack

- **React + Vite + TypeScript** — SPA servida no webview do Tauri.
- **Tailwind CSS** para estilização utilitária.
- **shadcn/ui** para componentes base (formulários, listas, dialogs, tabs,
  toasts). Componentes ficam no repo e são editáveis.
- **Vitest + Testing Library** para testes de componente/comportamento.
- Roteamento client-side leve (ex.: React Router) — sem SSR.

### Princípios

1. **UI depende só de use-cases/ports**, nunca de um repositório concreto. A
   injeção vem do composition root; a UI não conhece a origem dos dados.
2. **Estado assíncrono via camada de data-fetching** (ex.: TanStack Query) para
   cache, loading e revalidação — um único modelo de estados
   (loading/erro/vazio) para toda leitura, seja de dados locais ou da IA.
3. **Acessível e responsivo** dentro da janela desktop; suporte a tema
   claro/escuro.
4. **Markdown** como formato de corpo das entradas e de renderização das
   materializações.

### Layout / navegação

- Shell com navegação entre módulos: **Daily Log**, **Analyse**, **Settings**.
- **Daily Log**: editor de nova entrada + linha do tempo (lista) das entradas,
  com filtros por data, labels e propriedades. Gestão de labels e property defs.
- **Analyse**: seleção de período (semana/mês/quadrimestre) + filtros
  (labels/propriedades) → dispara o Processor → exibe a materialização (markdown)
  e histórico de análises anteriores.
- **Settings**: providers de IA (BYOK — escolher provider, modelo e informar a
  chave; ADR 0004) e, pós-MVP, backup/restore (login no provider de storage +
  seleção do arquivo; ADR 0005).

### Escopo funcional mínimo da UI (MVP)

Ver os comportamentos detalhados em [../mvp.md](../mvp.md). Em resumo, a UI deve
oferecer:

- **Daily Log**
  - Criar, editar e excluir entradas (corpo em markdown, data do fato).
  - Criar labels livremente (nome, cor) e associá-las a entradas.
  - Criar propriedades livremente (nome, tipo) e atribuir valores a entradas.
  - Visualizar entradas em linha do tempo, ordenadas por data.
  - Filtrar entradas por período, labels e propriedades.
  - Estados de loading / vazio / erro explícitos.
- **Analyse**
  - Escolher período (semana, mês, quadrimestre) e filtros (labels/props).
  - Disparar a geração da análise e ver progresso.
  - Ler a materialização resultante (markdown) e revê-la depois (histórico).
  - Estado de erro quando a IA falha, com opção de repetir.
  - Se nenhum provider de IA estiver configurado, orientar o usuário a Settings.
- **Settings**
  - Configurar providers de IA (BYOK): escolher provider, modelo e informar a
    chave, com validação da chave. Selecionar o provider/modelo ativo.
- **Global**
  - Feedback de sucesso/erro (toasts) em toda ação de escrita.
  - Estados de loading / vazio / erro consistentes.

## Consequências

**Positivas**

- shadcn/ui + Tailwind reduzem esforço de construir formulários/listas do zero.
- Camada de data-fetching padroniza os estados de loading/erro/vazio.
- UI testável por comportamento (Testing Library) contra use-cases mockados.

**Negativas / trade-offs**

- shadcn/ui é acoplado ao ecossistema React (decisão já assumida na ADR 0001).
- Onboarding de IA (BYOK) adiciona um passo antes de o Analyse funcionar; a UI
  precisa guiar essa configuração de forma clara.
- Markdown no corpo exige um editor/renderizador; começar simples (textarea +
  render) e evoluir se necessário.
